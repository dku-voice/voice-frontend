# AI language 연동 및 늦은 응답 보호 — 2026-11-19

후속 [음성 대기 개선](VOICE_WAIT_2026-11-19.md)에서 시간 초과·명시적 중지의 소켓을 분리하도록 보완했습니다. 아래의 타이머 미변경 및 같은 연결의 미확정 응답 설명은 이 작업 당시의 기록입니다.

## 기존 코드 확인

- `App.jsx`의 `connectWebSocket()` → `websocket.onmessage` → `handleAiMessage()`가 실제 수신 경로입니다. 기존 구현에도 최상위 language와 `ko`/`ja`/`es`/`th` 검증, `changeLanguage()` 연결이 있었습니다.
- `type: "order"`와 `item`을 확인한 뒤 `addToCart()`로 전달합니다. 실제 메뉴의 숫자 menuId 또는 기존 한국어 이름을 매칭하고, 기존 옵션 선택/optionIds로 `createCartItem()`과 `addCartItem()`을 호출합니다. 이 처리와 수량 계산은 수정하지 않았습니다.
- 언어는 기존 language state/ref, `src/i18n/index.js`, React 표시 번역, `LanguageSelector`를 재사용합니다. 별도 언어 상태 관리나 번역 시스템을 만들지 않았습니다.
- 발견한 문제는 voiceActive만 확인하므로, 수동 선택 전 요청이나 녹음 재시작 전 요청의 늦은 language가 현재 언어를 덮어쓸 수 있다는 점이었습니다.

## 자동 전환 방식

1. 실제 PCM 데이터를 기존 소켓으로 보낼 때 해당 소켓에 현재 녹음 세션과 수동 선택 이력을 로컬로 기록합니다. 계속 들어오는 PCM이 이미 기다리던 응답의 기록을 새 기록으로 덮지 않습니다.
2. `websocket.onmessage`에서 기존 JSON을 해석하고 language를 검증합니다. 음성 사용 중이고 현재 전송 기록에 속하는 결과일 때 기존 `changeLanguage()`를 호출합니다.
3. 수동 선택 전의 요청이나 이전 녹음 세션의 기록이면 **자동 언어 변경만 생략**합니다. 기존 주문 객체는 그대로 반환하므로 `type/order/item` 처리에서 조기 반환하지 않습니다.
4. 같은 언어 버튼을 다시 선택한 경우에도 그 선택을 이전 음성 요청보다 우선합니다. 이전 응답을 처리한 다음 새로 전송한 음성의 결과는 다시 자동 전환할 수 있습니다.
5. 연결이 교체된 경우 기존 `current()` 검사가 이전 소켓의 수신을 차단합니다. 언어 보호 기록도 소켓마다 구분합니다.
6. language가 없거나 잘못된 값이어도 기존 주문 처리를 계속합니다. 기존 order 응답은 해당 로컬 보호 창을 정리해 다음 결과를 계속 받을 수 있게 합니다. 관련 없는 KDS 상태 메시지나 잘못된 JSON은 보호 창을 소모하지 않습니다.

requestId, sequence, sessionId 등 새로운 필드는 메시지에 넣거나 읽지 않습니다. PCM 바이트·WebSocket 주소·백엔드 API와 응답 형태도 변경하지 않았습니다.

## 명세가 없어 완전히 보장할 수 없는 부분

현재 메시지에는 요청과 응답을 정확히 연결하는 확인된 식별자가 없습니다. 따라서 **같은 소켓에서 여러 음성 요청의 응답이 역순으로 오거나 중복 응답이 뒤늦게 도착하는 상황을 100% 구분할 수는 없습니다.** 시간만으로 임의로 특정 요청의 결과라고 판단하지 않았습니다.

이전 응답이 아직 미확정인 상태에서 새 녹음을 시작하면, 어느 요청의 결과인지 확정할 수 없는 첫 응답의 언어는 보수적으로 적용하지 않을 수 있습니다. 주문 데이터는 기존 흐름으로 계속 전달합니다. 다음 전송 창부터는 다시 언어 전환이 가능합니다.

AI 담당자에게 실제 배포 JSON 전체 예시, 응답 순서/중복 보장, 음성 요청 종료 기준, 요청과 응답을 연결하는 식별자 지원 여부를 확인해야 합니다. 기존 프론트의 type/order/item과 AI 저장소에서 앞서 확인한 status/items 구조 차이도 여전히 확인 대상입니다. 이번에는 새 구조로 바꾸거나 메뉴 ID/옵션/수량 대응을 추측하지 않았습니다.

기존 프론트는 한 order 이벤트를 기본 수량 1로 추가하고, 같은 옵션 조합을 합산합니다. 서버의 quantity를 새롭게 해석하는 수정은 하지 않았습니다. 실제 발화 수량이 의도대로 반영되는지까지 확인하려면 해당 수량 계약이 필요합니다.

## 유지한 기능과 검증

- 작업 시작 시점의 파일과 비교하여 번역 모듈/선택 버튼 컴포넌트, 메뉴·장바구니 도메인, 주문·결제 모듈, CSS, PCM/WASM/Worklet 파일이 그대로임을 확인했습니다. `createVoiceWait()` 본문도 바이트 비교로 동일합니다.
- 기존 `changeLanguage()`의 화면/TTS 반영을 재사용했습니다. 터치모드 타이머·카메라·나이 분석 기능을 별도로 수정하지 않았습니다. 기존 타이머의 응답 완료 판단도 유지하므로, 요청별 지연 표시까지 정확하게 대응시키는 일은 요청/응답 계약 확인이 필요합니다.
- **모의 검증:** 모의 JSON·WebSocket으로 4개 언어, 언어 미포함/잘못된 값, 수동 선택, 같은 언어 재선택, 음성 종료/재시작, 이전 소켓 차단을 확인했습니다. 실제 App의 수신 콜백과 실제 선택 버튼 핸들러를 실행했고, 언어 변경이 거절돼도 기존 주문 item이 전달되는 것을 확인했습니다. 실제 도메인 함수로 옵션·수량 합산·주문 API 요청 값이 유지되는 것도 확인했습니다.
- `npm test`: **169개 통과**(기존 161개 + 새 테스트 8개). `npm run lint`, `npm run build`, `git diff --check`: 통과.
- **실제 서버 검증:** 이번 작업에서는 실제 음성을 AI 서버에 전송하지 않았습니다. 실제 마이크 발화→AI 인식→언어 변경→주문/수량 반영 전체 성공을 검증했다고 볼 수 없습니다. 서버 응답 구조 확인 후 공동 테스트가 필요합니다. 실제 주문 생성/결제 승인/환불/관리자 변경도 실행하지 않았습니다.
- 커밋·푸시·PR·머지·배포를 하지 않았습니다.
