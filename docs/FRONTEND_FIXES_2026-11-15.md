## 2026-11-16 결제 복구 후 메뉴 담기 회귀 수정

앞선 복구 처리에서 미확정 인증이 남으면 메뉴와 장바구니 편집을 모두 잠근 것이 담기 차단의 원인이었습니다. 또한 영수증 GET이 완료·조리 중·취소·환불 상태를 반환해도 저장된 checkout을 갱신하지 않아 잠금이 지속될 수 있었습니다. 현재 메뉴 API와 로컬 프록시는 모두 HTTP 200이며 실제 메뉴 17개가 정규화·장바구니 항목 검증을 통과했습니다.

메뉴 담기·추천 담기·수량·삭제는 실제 승인 처리가 실행 중인 경우에만 잠그며, 결과 확인 대기 중에는 편집을 허용하도록 수정했습니다. 기존 인증·금액·주문 스냅샷은 별도로 유지하고 새 주문 결제는 이전 결과 확인 후 진행합니다. 결제가 확인되면 해당 옵션 조합의 결제 수량만 차감해 나중에 추가한 메뉴·추가 수량·다른 옵션을 보존합니다. 같은 주문을 반복 조회해도 한 번만 차감하도록 영수증 처리 상태를 관리합니다.

같은 주문의 readReceipt GET은 정상 terminal 응답을 paid/closed로 동기화합니다. PENDING·조회 실패·다른 주문은 기존 인증을 유지합니다. 상태 변경 revision·스냅샷·조회 시작 순서를 모두 대조해 늦은 GET이 새 승인/주문 상태를 덮지 않도록 했습니다. 복구 getter는 저장된 주문과 맞지 않는 메모리 URL 후보를 무조건 잠금으로 취급하지 않습니다. 실제 주문 결과를 확인하기 위해 승인 POST를 자동 재실행하지 않습니다.

최종 테스트 **141개**, lint/build와 diff 공백 검사가 통과했습니다. 미확정 인증 상태에서도 ACTIVE 메뉴 담기·장바구니 편집이 활성화되는 SSR 회귀, 완료/환불 후 복구 해제, 결제 수량 정리·추가 상품 보존, 동시 영수증 조회 경합을 검증했습니다. 실제 서버에는 메뉴 GET만 실행했으며 주문 생성·결제 승인·환불은 실행하지 않았습니다. 아래의 이전 기록 중 장바구니 전체 잠금 설명은 이 변경으로 대체됩니다.

## 2026-11-16 토스 인증 후 오류 복구 보완

토스 인증 후 첫 주문 조회가 실패해도 인증 결과를 잃지 않도록, 검증된 callback을 조회 요청 전에 sessionStorage에 보관합니다. 주문번호·금액·선택 결제수단·기존 인증키를 확인하며 다른 키나 주문으로 바꾸지 않습니다. 저장에 실패하면 조회·승인을 시작하지 않고 메모리에서도 중복 요청 차단 상태를 유지합니다. 실패한 callback URL은 임의로 지우지 않으며 정상 완료 또는 서버에서 종료 상태를 확인한 경우에만 정리합니다.

다시 결제 화면을 열면 기존 인증 결과가 있는지 확인하고, 새 인증창 대신 같은 주문을 계속하는 버튼을 표시합니다. 아직 승인 요청을 보내지 않은 경우는 `결제 계속하기`, 승인 요청 후 결과가 불확실한 경우는 `결제 상태 확인`입니다. 후자는 조회만 하며 승인 POST를 반복하지 않습니다. 인증 기록 복원만으로 새 승인 요청을 자동 실행하는 동작은 추가하지 않았습니다. 토스에서 성공 URL로 처음 돌아온 정상 callback 처리는 기존 승인 흐름을 유지합니다.

결과 확인 중에는 장바구니 변경과 새 주문·TEST 승인 전환을 차단합니다. 이전 버전에서 `confirming`에 TOSS 거래키를 남긴 기록도 안전하게 조회 복구합니다. 이전 코드가 첫 조회에 실패한 뒤 인증키를 전혀 저장하지 않고 URL까지 지운 `ready` 기록은 소실된 키를 복구할 수 없습니다. 취소·환불 등 종료 상태가 서버 조회로 확정되면 인증 참조를 정리하고 사용자가 새 주문을 시작할 수 있게 했습니다.

오류는 주문 생성·주문 상태 조회·결제 승인을 구분해 표시합니다. 오류 화면에 주문번호와 숫자 주문 ID를 보여주며 펼침 영역에는 HTTP 메서드·쿼리 없는 요청 경로·상태만 표시합니다. 토큰·본문·비밀번호·paymentKey는 진단 정보에 넣지 않고, 알려진 결제키가 오류 문구에 있으면 가립니다. 늦게 도착한 결과와 KDS 화면에서도 오류 객체를 그대로 렌더하지 않습니다.

최종 자동 테스트 **124개**, lint/build와 diff 공백 검사가 통과했습니다. 첫 GET 500 후 새 manager 복구, 승인 결과 유실 후 GET-only 확인, 위변조·저장소 실패·기존 기록 호환과 복구 화면 SSR을 검증했습니다. 실제 서버의 주문 생성·결제 승인·재승인 요청은 실행하지 않았습니다. 이 수정은 프론트의 인증 결과 소실과 재시도 처리를 보완하며, 백엔드 주문 조회 API의 HTTP 500이나 서버 DB 조회 오류 자체를 고치는 변경은 아닙니다. 사용자 주문의 실제 실패 지점은 다음 오류 화면의 주문 ID·요청 경로와 서버 로그로 확인해야 합니다.

## 2026-11-16 로컬 결제 준비의 CORS 오류 안내 수정

원격 서버에 Origin을 명시한 GET `/api/menus` 및 주문 생성의 사전 요청인 OPTIONS `/api/orders`를 비교했습니다. Origin=`http://127.0.0.1:5173`은 두 요청 모두 403과 `Invalid CORS request`를 반환했습니다. Origin=`http://localhost:5173`, `https://dku-voice.com`은 GET/OPTIONS 모두 200으로 허용됐습니다. 주문 POST 자체는 실행하지 않았습니다.

앱은 주문을 서버에서 먼저 준비한 후 위젯을 표시하므로, 주문 준비가 거절되면 토스 위젯 단계에 도달하지 않습니다. 기존 공통 클라이언트가 공개 주문 API의 401/403까지 세션 만료 문구로 바꿔 오해를 일으켰습니다. 공개 요청은 서버 메시지 또는 HTTP 요청 거절 안내를 표시하고, 보호 요청만 로그인 안내와 세션 정리를 유지하도록 수정했습니다. 공개 요청에 직원/관리자 토큰을 추가하지 않았습니다.

일반 개발 접속 주소를 **http://localhost:5173/** 로 안내합니다. 이 주소의 HTML 200, 실제 메뉴 17개 응답 200, 로컬 OPTIONS 204와 허용 출처를 확인했습니다. 로컬 OPTIONS 응답은 Vite가 처리할 수 있으므로, 위의 원격 OPTIONS 200 비교를 별도 근거로 사용합니다. 프록시 Origin을 숨기거나 재작성하지 않았으며 백엔드 보안/CORS 설정도 바꾸지 않았습니다. 최종 자동 테스트 107개 및 lint/build가 통과했습니다. 실제 주문 생성·결제 인증·승인은 미검증 상태입니다.

## 2026-11-16 메뉴 옵션 중복 보완

실제 메뉴 API는 HTTP 200, success=true, ACTIVE 메뉴 17개로 정상 응답하게 되었습니다. 다만 9개 메뉴의 options 배열에 동일 optionId가 반복되어 기존 프론트 검증이 실패하고 예시 메뉴의 담기 버튼이 잠겼습니다. 예를 들어 데리버거는 8종 옵션이 56행으로 반환됐습니다.

메뉴별로 optionId와 한국어·영어 이름, optionType, extraPrice가 모두 같은 옵션만 한 번씩 정리하도록 수정했습니다. 모든 반복 행도 기본 형식 검증을 먼저 거치며, 같은 ID의 내용이 다르거나 잘못된 가격·종류·ID인 경우는 계속 거부합니다. 양념감자 소스 한 개 선택, 옵션 추가금 한 번 계산, 실제 서버 menuId/optionId 사용과 원본 응답 보존을 유지합니다.

로컬 5173 프록시로 실제 서버 메뉴를 GET하고 현재 도메인 함수로 17개 메뉴의 장바구니 항목과 주문 요청 데이터를 메모리에서 구성해 검증했습니다. 데리버거 2,800원+치즈 500원=3,300원 등 옵션 가격도 확인했습니다. 실제 주문 POST·결제 승인이나 브라우저 클릭 검증은 실행하지 않았습니다. 최종 테스트 105개, lint/build와 diff 공백 검사가 통과했습니다. 백엔드의 옵션 중복 반환 자체는 여전히 별도 개선 대상입니다. 아래는 11월 15일 점검 기록입니다.

## 수정한 내용

- 로그아웃: 서버 응답을 기다리기 전에 이 기기의 세션·KDS·관리 데이터부터 정리합니다. 서버 토큰 폐기에 실패하면 별도 메시지를 표시합니다.
- 인증: HTTP 401/403 모두 현재 요청의 토큰에 한해 만료 처리합니다. JWT `exp`가 있으면 해당 만료 시각을 사용하며, 서버의 서명 검증을 대신하지 않습니다. 장기 토큰은 브라우저 타이머 상한에 맞춰 나눠 예약합니다.
- KDS: GET 이후 SSE나 이 기기의 조작으로 실제 변경된 주문만 보존합니다. 다른 주문의 이벤트 때문에 이전 PAID 상태가 새 PREPARING 결과를 덮거나 완료 주문을 남기는 병합을 수정했습니다.
- 날짜: 관리자 통계의 초기 날짜를 한국시간 기준으로 만듭니다.
- 관리자 메뉴: 서버가 반환한 원본 메뉴를 고객용 분류와 별도로 보관합니다. 응답에 포함된 INACTIVE 메뉴는 관리자 목록에서 유지하며 고객 화면에서는 제외합니다. 서버가 INACTIVE를 아예 반환하지 않는 경우는 별도 API가 필요합니다.
- 결제: 장바구니 결제하기 → 서버 주문 생성/재조회 → 서버 총액으로 위젯·약관 자동 표시 → 최종 결제하기 → 토스 인증 → 콜백 검증 → 백엔드 TOSS 승인 → 주문 재조회 → PAID/PREPARING/COMPLETED 영수증 순서로 연결했습니다.
- 결제 화면의 세 버튼을 하나의 결제하기로 통합했습니다. 위젯의 실제 ready 이벤트와 필수 약관을 확인하며, 준비 실패 시 같은 버튼으로 재시도할 수 있습니다.
- 결제 중 AI 이벤트가 화면을 바꾸거나 장바구니를 변경하지 않도록 했습니다. 늦게 도착한 초기 영수증 조회가 결제 완료 결과를 덮지 않도록 했습니다.
- 결제 콜백의 주문번호·금액을 저장된 주문과 대조하고, 백엔드에는 숫자 DB 주문 ID를 전달합니다. paymentKey는 승인 요청의 pgTransactionId로 사용합니다. 성공 URL에 도착한 것만으로 성공을 표시하지 않습니다.
- 주문/승인 중복 방지, 이미 결제된 주문 재조회, 승인 응답 유실 후 PAID 복구를 유지했습니다. 결과가 불명확한 승인은 자동 재시도하지 않습니다.

## 결제수단과 테스트 환경

일반 실행에서는 `test_gck_` 위젯 키만 허용합니다. 기존 클라이언트 키 값을 바꾸거나 프론트에 시크릿 키를 추가하지 않았습니다. 선택된 신용·체크카드/Apple Pay는 CARD, 카카오페이는 KAKAO_PAY, 네이버페이는 NAVER_PAY, 토스페이는 TOSS로 저장합니다. 이 매핑은 현재 로컬 백엔드 enum에 있는 값에 한정되며, 서버는 실제 PG 응답과 내부 결제수단의 일치도 검증해야 합니다.

계좌이체·PAYCO·그 외 미확정 수단은 임의로 CARD로 기록하지 않고 인증 요청 전에 안내합니다. 토스가 표시하는 전체 수단을 모두 지원한다고 검증한 상태는 아닙니다. 모든 수단이 필요하면 백엔드 결제수단 계약과 위젯 상점 설정을 함께 확정해야 합니다.

`npm run dev:mock`의 loopback 전용 local-mock 모드에서는 외부 토스 대신 기존 TEST 승인으로 동작합니다. 버튼 이름은 동일한 결제하기 하나입니다. 모의 환경 키는 빈 값이며 외부 요청을 하지 않습니다. 일반 실행에서 이 경로로 자동 대체하지 않습니다.

1. 메뉴 GET은 11월 16일 정상화됐고, 주문 ID 4·7의 GET은 11월 17일 21:34 KST에 HTTP 200으로 확인했습니다. 이전 500 기록과 구분하며, KDS/관리자 조회의 인증 오류와 정상 조회 및 전체 결제 흐름은 별도로 확인해야 합니다.
2. 프론트 테스트 위젯 클라이언트 키와 같은 세트의 시크릿 키를 서버에서 사용해야 합니다. 별도 API 개별 연동 키와 섞지 않습니다.
3. 토스 요청의 `orderId`는 `POST /api/orders`에서 받은 `orderNumber` 문자열입니다. 프론트가 `/api/payments/confirm`에 보내는 `orderId`는 숫자 DB ID입니다. 11월 16일 원격 main 코드에서 백엔드가 **저장된 orderNumber**를 토스 승인에 전달하도록 수정된 것을 확인했습니다. 오래된 로컬 백엔드 사본과 구분하며 실제 PG 승인 결과는 공동 테스트가 필요합니다.
4. 승인 DTO는 기존 필드를 유지합니다: pgProvider=TOSS, pgTransactionId=토스 paymentKey, orderId=숫자 DB ID, amount=서버 totalPrice, method=저장된 지원 결제수단. 서버에서 PENDING 상태·금액·실제 PG 결과를 검증해야 합니다.
5. PAID뿐 아니라 조리/완료/취소/환불 상태의 재승인 차단, 잠금 만료 시 중복 처리, PG 승인 성공 뒤 DB 저장 실패 복구를 검증해야 합니다.
6. 주문 생성 응답 자체가 유실되면 프론트는 DB ID를 알 수 없어 재생성을 차단합니다. 서버에서 중복 생성 방지/주문 재조회 계약 또는 담당자 확인이 필요합니다.
7. 배포 프론트는 `/payment/success`, `/payment/fail`에서 SPA를 제공해야 합니다. Vite 개발 서버에서는 해당 URL을 처리할 수 있습니다. 새 프론트 빌드와 키 설정이 실제 배포에 반영됐는지도 확인해야 합니다.
8. 비활성 메뉴 전체 조회 및 AI 연령/추천 요청·응답 계약은 여전히 확인이 필요합니다. 없는 API를 만들거나 백엔드·AI·Nginx·Docker를 수정하지 않았습니다.

## 검증과 한계

최종 `npm test` **102개 통과**, `npm run lint`·`npm run build` 통과, `git diff --check` 통과입니다. 테스트는 실제 프론트 API/checkout 모듈과 로컬 모의 HTTP, 주입한 가짜 토스 SDK를 사용합니다. ready·약관·선택 수단·리다이렉트·콜백·서버 금액·중복·응답 유실·새로고침과 KDS 경쟁 조건을 검증합니다. 화면 SSR에서는 결제 버튼이 하나이며 렌더만으로 주문이나 승인을 요청하지 않는지 확인합니다. 실제 모듈 전체를 조합한 메모리 테스트에서도 CARD/KAKAOPAY 선택과 새로고침 후 승인, 중복 콜백을 확인했습니다. 로컬 Vite의 성공·실패 콜백 경로가 SPA HTML을 반환하는 것도 확인했습니다.

자동 점검에서는 실제 운영 주문 생성, 토스 인증/승인, 환불, 관리자 데이터 변경을 실행하지 않았습니다. 사용자의 수동 토스 인증 후 주문 조회 실패 제보를 바탕으로 조회만 재검증했습니다. 실제 브라우저 인증부터 서버 승인까지의 전체 성공은 아직 검증되지 않았습니다. 위 최신 서버 확인 결과를 기준으로 테스트 환경에서 메뉴→장바구니→토스 테스트 인증→승인→영수증→KDS를 공동 확인해야 합니다.

이번 변경은 develop 대상 PR에서 검토하며, 머지·배포 및 전체 결제 성공 검증은 별도입니다.
